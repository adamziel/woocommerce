Executive Findings

  1. Product variations and attributes are the strongest first issue. WooCommerce core itself warns that WC_Product_Variable::get_available_variations( 'array' ) is expensive for many variations. Local measurements show steep CPU and payload growth: roughly 6 seconds and 1 MB of JSON-like payload for a single 1,000-variation product in the CLI profile.
  2. Product/admin search and filter ID materialization are the second issue. On a 5,000-product fixture, admin search built a 5,002-ID post__in array before pagination, Store API on_sale=true prepared 2,500 IDs, and Product Collection large ID intersections spent measurable PHP time before the query ran.
  3. Orders are improved by HPOS but not solved for every shape. HPOS gives dedicated order tables and indexes, but the default All admin search can still fan out into expensive scans. On a 20,000-order fixture, a complete email search through All took 185 ms while the indexed email path took less than 1 ms.
  4. Bookings performance is mostly outside this repo. Core can approximate Bookings pressure with product type/data-store hooks, cart hooks, Store API hooks, and booking-like order meta. The real availability calendar and slot search logic lives in WooCommerce Bookings, not in core.

Code Paths

Variations And Attributes

  • includes/class-wc-product-variable.php: get_available_variations(), get_available_variation(), sync().
  • includes/data-stores/class-wc-product-data-store-cpt.php: find_matching_product_variation() loads all child attribute meta and scans in PHP.
  • includes/data-stores/class-wc-product-variable-data-store-cpt.php: child reads, variation attributes, price/stock sync, and large child IN (...) query shapes.
  • src/Internal/ProductAttributesLookup/*: attribute lookup maintenance, filtering, and regeneration.
  • src/Internal/ProductFilters/FilterData.php: product filter counts can materialize all matching product IDs with posts_per_page = -1.

Orders

  • src/Internal/DataStores/Orders/OrdersTableQuery.php: HPOS order query builder.
  • src/Internal/DataStores/Orders/OrdersTableSearchQuery.php: HPOS order search, including fallback search paths.
  • includes/data-stores/class-wc-order-data-store-cpt.php: legacy post/meta order queries and legacy order search.
  • src/Caches/OrderCountCache*.php: order count caching and priming.

Bookings Boundary

Core does not include WC_Product_Booking or booking availability logic. The relevant core extension points are product type registration, product data stores, cart item data, Store API payment requirements, checkout line items, and HPOS/order meta storage. Real slot lookup, resources, availability rules, in-cart holds, and booking calendar performance require the WooCommerce Bookings plugin.

Limitations

  • The largest local fixtures so far are 1,000 variations on one parent, 5,000 products for search/filter lanes, and 20,000 HPOS orders. That gives strong query-shape evidence, but it is still smaller than the 100k+ and million-order stores discussed in large-store reports.
  • CRUD seeding is faithful but too slow for repeated large sweeps. The new bulk variation seed path is useful for read/matching profiles, but write-path and hook behavior must still be verified with CRUD fixtures.
  • The current measurements run in WP-CLI inside Docker. HTTP/k6 and browser-facing paths still need to be measured after the query candidates are narrowed.
  • No premium WooCommerce Bookings source is present. Bookings conclusions are therefore about core extension points and documented product behavior, not the private implementation.
