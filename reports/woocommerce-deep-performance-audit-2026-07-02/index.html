Tax Postcode Range Index Probe

The remaining tax prequery is not safely reducible with a simple prefix filter: a prefix-only query would miss valid broad ranges such as 90000...99999 and alphanumeric ranges handled by wc_postcode_location_matcher(). A copied-table schema probe tested whether persisted range bounds could make the lookup indexable.

ShapePlanRowsMeasured timeArtifact

Developer handoff: a production fix should not use MySQL casts as the final implementation. This is a schema/migration project, not a small query-only PR.

Shipping Postcode Matcher Audit

The shipping path has the same high-level problem as taxes, but with a broader matcher call: WC_Shipping_Zone_Data_Store->get_zone_id_from_package() loads every postcode rule, then wc_postcode_location_matcher() performs range/wildcard matching in PHP before the final zone query excludes nonmatches with a generated NOT IN list.

PHP-only split-query postcode lookupCandidate loaded all postcode-rule zone IDs, queried exact/wildcard candidates via IN (...), and loaded range rows via LIKE '%...%'. Range fixture: baseline median 123.517ms, candidate 129.583ms; exact fixture: baseline 121.558ms, candidate 126.281ms.Rejected. It adds two queries and does not remove the all-rule scan. Even exact-postcode data still pays the DISTINCT zone_id scan plus an empty range probe.JSON

The PHP matcher rewrite was rejected by benchmark. Adjacent baseline request p95 was 109.683ms. Candidate 1 p95 was 109.953ms; candidate 2 p95 was 113.576ms with worse DB p95. XHProf showed candidate 2 reduced array_map calls from 20,263 to 263 and matcher inclusive time from 40.240ms to 34.178ms in a one-request profile, but that did not translate into a reliable request-level improvement.

A second PHP-only branch that tried to split exact/wildcard lookup from range rows was also rejected. It was tested on the gateway-active stack with 8,000 shipping zones and 12,000 tax ranges. On the all-range shipping fixture it raised query count from 120 to 122 and median SQL time from 58.40ms to 62.37ms. On an exact-postcode rewrite of the same shipping fixture it raised median SQL time from 58.14ms to 63.31ms. The exact IN (...) lookup itself was cheap, but the candidate still needed an all-zone postcode-rule scan and a range probe.

Developer handoff: normalize shipping postcode rules when they are saved, store exact/wildcard candidates separately from numeric range bounds, and query only destination-relevant candidate postcode rows before invoking the existing PHP matcher as a compatibility fallback. The final zone query should consume a short matched-zone candidate list instead of deriving a large nonmatch list from every postcode rule.
