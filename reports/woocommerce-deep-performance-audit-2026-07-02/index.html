Ranked Problems

RankProblemMeasured conditionsSlowest evidenceDeveloper handoff
1 Checkout/order creation write amplification Store API checkout, 20 distinct line items, WooCommerce core only, HPOS enabled, MySQL 8, PHP 8.3. CRUD-invariant 48-worker report shows 5,471ms HTTP p95, 5,110ms DB p95, 2,688 query p95. Across profiled samples: order item meta inserts dominate, followed by reserved stock inserts, product lookup table rewrites, order item inserts, repeated itemmeta cache probes, stock meta updates, and sales-count updates. Start in StoreApi\Routes\V1\Checkout, order creation/save, WC_Abstract_Order::save_items, ReserveStock::reserve_stock_for_order, and product stock/sales lookup refresh. The likely fix area is bulk persistence and avoiding per-item metadata existence/cache probes.
2 Concurrent checkout stock/order writes 40 concurrent Store API checkouts against managed stock. CRUD-invariant profiler: 1,871ms server p95, 1,741ms DB p95, 519 query p95. Top SQL totals in the mined profiler: wp_wc_orders_meta inserts, wp_woocommerce_order_itemmeta inserts, wp_wc_orders_meta deletes, order-note wp_comments/wp_commentmeta writes, and wp_posts.comment_count updates. Separate stock reservation logging from the hot reservation path, batch meta writes/deletes, and profile lock/wait behavior around reservation and stock decrement SQL.
3 Variable product variation formatting Variable product with hundreds of variations. Runtime artifacts show 224 profiled samples, 1,948ms server p95, 265ms DB p95, 885 query p95, with some HTTP 500s in older artifacts. 121,607 repeated term lookups across samples: WC_Product_Variation_Data_Store_CPT->generate_product_title -> wc_get_formatted_variation -> get_term_by -> WP_Term_Query. This maps to the recent variation PRs. The developer handoff is to avoid per-variation term lookup/title sync work in available variation payload generation and cache taxonomy term-name maps per request.
4 HPOS admin broad search and list count cost HPOS admin order search all-filter. CRUD-invariant report: 826ms server p95, 516ms DB p95, 126 query p95. Pathological report: 2,880ms HTTP p95, 2,751ms DB p95 at larger order scale. Repeated wide COUNT(*) and ID queries over wp_wc_orders with OR/LIKE/subquery search across transaction ID, billing email, order IDs, meta, addresses, and order items. Cache priming then adds postmeta/order-itemmeta/product term work. Fixes split across indexed search routing, short-circuiting counts, and reducing list-table cache priming when the first page is partial or search selectivity is low.
5 Store API product collection-data facet counts Store API products/collection-data with price, stock, rating, category, and attribute counts. CRUD-invariant report: 267ms server p95, 150ms DB p95, 51 query p95. Pathological report reached 6,963ms HTTP p95 at larger catalog scale. Top SQL is count aggregation over posts/postmeta/product lookup/term relationships, especially stock status and taxonomy/attribute count queries over broad product ID subqueries. Work in ProductCollectionData, ProductQueryFilters, and filter-count SQL. The existing PR split around product-ID subqueries and post__in merging is aligned with this problem.
6 Analytics stats broad aggregates Woo Analytics revenue/products stats with forced cache refresh. CRUD-invariant report: revenue 217ms server p95, products 147ms server p95. Pathological report reached 2,595ms and 2,304ms HTTP p95 at larger analytics-row scale. Revenue stats spend time in distinct product counts and monthly SUM/COUNT aggregates over wc_order_stats, coupon lookup subqueries, and product lookup joins. Products stats spend time in SUM/COUNT DISTINCT over wc_order_product_lookup. Review report datastore query shapes, cache invalidation/refresh behavior, and whether high-cardinality aggregates can be precomputed or split by narrower indexed windows.
7 Core tax postcode matching scales linearly New core lane: one Store API cart update with one taxable shippable product, US/CA/94105 address, WooCommerce only, 8,000 shipping zones/methods, 12,000 tax postcode ranges. Result: 101ms HTTP p95, 92.5ms PHP p95, 55.7ms DB p95, 67 query p95. Per request averages from 8 samples: tax main joined query about 22ms, tax postcode range prequery about 10ms. MySQL plan uses tax_rate_class for about 6,044 rows, temp table/filesort, joins locations by tax_rate_id, and dependent subqueries for city/postcode existence. Primary issue is SQL shape, not just missing indexes. Candidate fixes: precompute searchable postcode range representation, avoid broad GROUP BY over all same-class rates, use anti-joins/derived tables instead of dependent subqueries, and add a composite index only after rewriting predicates to use it.
8 Core shipping postcode-zone matching loads all postcode locations Same new core lane. Shipping contributes about 5ms/request loading all postcode locations and about 3ms/request selecting the matching zone at 8,000 generated zones. WC_Shipping_Zone_Data_Store->get_zone_id_from_package first runs SELECT zone_id, location_code FROM wp_woocommerce_shipping_zone_locations WHERE location_type = 'postcode', then builds a large NOT IN (...) exclusion list for the zone query. For larger merchants, replace all-postcode loading with indexed candidate selection or persisted normalized ranges. Avoid constructing a large NOT IN list after PHP matching.
9 Gateway stack bootstrap/admin settings overhead Activated official/free gateway plugins from WordPress.org: Stripe 10.8.3, PayPal Payments 4.1.0, WooPayments 10.9.0. No gateway credentials configured; most gateway methods are disabled. Cart-total p95 rose from 101ms to 133ms and query p95 from 67 to 126. Authenticated admin payment settings pages ranged from about 946ms median on the list view to 1,357ms median on the PayPal settings section. Top gateway-specific evidence: WooPayments/Jetpack connection authorization repeatedly updates and deletes options on settings pages; WooPayments localization primes transients; active gateway registry adds hundreds of option reads. Admin pages are also dominated by the Woo admin menu order-count query over HPOS orders. Separate core admin-menu count cost from gateway provider/settings cost. Then profile configured gateway flows with credentials or mocked gateway API responses. The current result proves bootstrap/settings overhead, not payment authorization or renewal behavior.

Static Audit Notes

AreaCode pathConcern
TaxesWC_Tax::get_matched_tax_ratesCart totals cache rates per tax class in request scope, but the cold lookup still walks all postcode ranges and then runs a broad grouped join for matching rates. The single-rate helper methods is_compound, get_rate_label, get_rate_percent_value, and get_rate_code still query by ID when callers pass IDs instead of hydrated rate rows; this is a separate N-query audit target.
ShippingWC_Shipping_Zone_Data_Store->get_zone_id_from_packageThe matcher loads every postcode location into PHP, runs postcode/range matching there, then excludes nonmatches via a generated NOT IN list. The existing location_type_code(location_type(10), location_code(20)) index helps only with the location type filter in the measured shape.
Prettyboymp commit contextRecent trunk historyRecent performance work clusters around object caching, HPOS datastore caching, product variation payloads, shipping-zone read-multiple support, analytics lazy loading, and tax/cart query reductions. The current slow paths line up with those themes: repeated object hydration, broad aggregates, and lookup shapes that need preselection rather than post-filtering.
